## 刻意偏离（写给未来的自己）

1. **间距仍用固定 8px 基数**，不采用 Heron 的 `vw` 流式 rem —— 看板要稳定节奏。
2. **字阶仍固定**，不流式 —— 同上。
3. **保留 8 个功能数据色**（Heron 近单色）—— 图表要区分 5 个工具，砍了就读不懂。
4. **不采纳**自定义光标 / Lenis 滚动劫持 / 跑马灯 —— 营销站动效。
5. **颗粒压到极淡**（≤3%）—— 数据可读性优先。
6. **Inter 替代 BT Grotesk** —— 授权字体不可分发。

## 图表制图化（第二轮）

起因：`.grid-line` 原本是一条 `stroke: var(--line-soft)` 的实线——比发丝线还淡，
既不像网格也不像刻度，四角不收口，图是「浮」在纸上的。按制图板重画：

| 元素 | 之前 | 现在 |
| --- | --- | --- |
| 横向网格 | 4 条实线 | 3 条**测量虚线**（1px 实 / 5px 空）+ 1 条基线实线 |
| 基线 datum | 与网格同款 | 单独一条实线 `--line` |
| 左轴 datum | 无 | 竖发丝线定住坐标系 |
| 四角 | 无 | **`+` 定位十字** |
| x 轴 | 只有文字 | 每刻度一条 3px 短竖线 |
| 数据端点 | 无 | 末端 **4px 方块**（随揭示淡入） |
| hover | 实线 | 虚线 + 顶端游标 `+` |
| 环形图 | 一条粗环浮在纸上 | **内外两道 datum 圈 + 12 点起始刻度** |
| 构成条 | 色块直接相接 | 段间留 **1px 纸缝** |
| 表格 | 表头下 `--line` 细线 | 表头下压 **墨色 datum 线**；数值列 `nowrap` 保持小数点成列 |

刻意保留：`工具 × 模型` 矩阵的填充是**墨阶密度**（`color-mix(--ink N%)`），
与新热力图同源，属制图板语汇，不动。

## 第三轮：性能 / 时间范围 / 切栏滚动 / 模型速度

### 1. 切时间范围要等 ~3s

实测 `/api/dashboard` 冷启：全历史 **1.36s**、带筛选 0.37s。逐个查询 profile 后找到三处：

| 问题 | 病因 | 修复 | 效果 |
| --- | --- | --- | --- |
| `sessions` 207ms | 对每个会话各发一条 `SUM() WHERE session_id=?`，而 **`session_id` 上没有索引** → 20 次全表扫描 | 加 `idx_events_session` + 改成一次 `GROUP BY` + `LEFT JOIN` | **207ms → 21ms** |
| 每次切范围都重算 17 个查询 | 没有缓存 | 加 15s TTL 的 payload 缓存（按范围键），扫描完成后失效 | 冷启 0.86s → **重复切 2ms** |
| 切换时没有任何反馈 | `loading` 只用在开机屏 | 顶栏下加橘红扫描线 + 正文变淡（**保留旧数据**，不是留白） | 有反馈了 |
| `sessions` **忽略 from/to** | 查询里根本没写范围条件 | 补上 `date(started_at/1000,'unixepoch')` 过滤 | 口径 bug 一并修掉 |

### 2. 时间范围

- 新增 **今天**（`from = to = 今天`）与 **自定义**（两个原生 `date` 输入 + 清除）。
- preset 的窗口语义改成「含今天的 N 天」（原来 `daysAgo(7)` 实际是 8 天）。
- **修掉一个真 bug**：`daysAgo` 用的是 `toISOString()`（UTC），东八区晚上 8 点后
  「今天」会算成明天，于是查不到当天数据。改用本地年/月/日拼接。

### 3. 点栏不跳转

原来滚到 `document.querySelector("[data-reveal]")`——那是**第一个区块**，
而区块高度依赖内容（图表 SVG 按容器宽算高），切栏时页面总高度大幅变化，
「量一次、滚一次」经常落空；偏移也没算上粘性顶栏（差约 60px）。

改为滚一个**高度稳定的锚点** `.tab-anchor`（紧贴标签栏下方），偏移 = 标签栏 + 顶栏高度，
并在下一帧校正一次。实测四个栏切换后锚点都稳定落在粘性栏下方 24px。

### 4. 新功能：模型速度

新增 `/api/dashboard` 的 `speed` 字段与「总览 → 模型速度」区块：

- **每个工具最近一次会话**：工具 / 模型 / 路径 / 输出速度 / 每请求 / 总吞吐 / 活跃分钟。
- **按模型排行**：当前范围内各模型的输出速度，含请求数与活跃分钟。
- 同名行合并：按**裸模型名**分组，否则 `opencode-go/deepseek-v4.1-flash`
  和 `deepseek-v4.1-flash` 会各占一行、显示成同名两行。

> **口径（重要）**：实测 92,852 条事件的 `latency_ms` / `ttft_ms` **全为 0**，
> 各工具日志里几乎没有逐请求耗时。所以速度量的是**吞吐**
> （`output_tokens ÷ 活跃分钟`），不是首 token 延迟，界面上直接标明。
> 唯一存在的真实延迟数据是 Codex `task_complete` 的
> `duration_ms` / `time_to_first_token_ms`（实测 12.0s / 5.1s / 3.2s），
> 需要新增表 + 采集逻辑 + 全量重扫才能补上——**本轮未做**，见下方。

## 第四轮：速度口径改为「生成区间」（tok/s）

用户给出参考图：要的是 **tok/s**，且要按「生成区间」估算，不是按分钟摊平。

### 1. 先查清日志里到底有没有耗时

92,852 条事件的 `latency_ms` / `ttft_ms` **全为 0**——逐请求耗时没有被采集。
所以速度只能估算：**同会话内相邻两次请求的间隔 = 后一次的生成时长**。

实测区间分布（92,353 个样本）：

| 区间 | 占比 | 处置 |
| --- | --- | --- |
| < 1s | 6.0% | 剔除（同批抖动） |
| 1s–300s | **92.6%** | 保留（真正的生成） |
| ≥ 300s | 0.9% | 剔除（用户走开；不剔除会把全站从 26 tok/s 拉到 0.8） |

抽查单个会话的逐区间速度：6.3 / 12.7 / 18.8 / 22.0 / 24.7 / 30.1 / 35.4 tok/s——
量级与参考图（31.2 / 53.5 / 52.2 / 35.1）一致。

### 2. 顺带发现旧口径高估 10 倍

| 旧口径 | 问题 | 偏差 |
| --- | --- | --- |
| 活跃分钟（分母 = 有请求的分钟数） | 一分钟记满 60 秒，实际只生成 8 秒 | **低估约 7 倍** |
| 完成秒分桶（分母 = 有完成的秒数） | 整次响应被当成 1 秒 | **高估约 10 倍** |

两种口径**同一屏同时出现**：「用量与成本」注脚显示 251 tok/s，
而「模型速度」显示 26.3 tok/s。现在全站统一到生成区间。

### 3. 实现

- `speed()` 重写：一次窗口扫描按 `(日, 时, 工具, 模型)` 分组（全历史只有 1,122 行 / 228ms），
  其余维度（`byModel` / `byTool` / `byDay` / `byHour` / `overall`）在 JS 里 rollup——
  分四次 `GROUP BY` 要 ~900ms。
- 返回 `tok_per_sec` / `intervals` / `gen_seconds` / `out_per_req`，卡片以 tok/s 为主角。
- 「用量与成本」注脚、「时段分布」、高产时段一并改用该口径（`data.speed`）。
- 「生成速度的峰值秒（162,835 tok/s）」改写成「**单秒完成量峰值**」并注明不是速率——
  一次响应的输出会在完成那一秒整笔入账。

### 4. 未处理（记录）

- `rate()` 仍在算已不再被界面引用的 `byDay` / `byHour` / `byTool` / `recent`
  （全历史约 430ms）。它同时是文档化的独立接口 `GET /api/rate` 且被
  `server/rate.test.js` 覆盖，本轮不动，留作后续优化。
- x 轴上「时段分布」的 y 轴没有刻度，仅靠 hover 显示数值。

### 5. 顺带修掉：opencode 的 cwd 100% 为 null

面板一开始只有 2 张卡（codex / claude-code），但装了 5 个工具、有 4 个在跑数据。
两个独立原因：

1. `latestByTool` 以 `sessions` 表为主表，而 **opencode 采集器根本不写 `sessions`**
   （2,443 条事件、11 个会话 id 全在事件表里，`sessions` 里一条都没有）。
   → 改成以**事件表**为准（利用 SQLite「只含一个 MAX() 时裸列取自最大行」的保证），
   `sessions` 只用来补标题。
2. 采集器里的 `SELECT id, directory, worktree FROM session_v2` ——
   **2.0.x 的 `session_v2` 没有 `worktree` 列**，整条 SQL 抛
   `no such column: worktree`，被 `catch {}` 静默吞掉，于是 cwd 全为 null。
   → 改成先读 `PRAGMA table_info` 再按真实列名拼 SQL。

### 6. 我造成的数据损失（必须记录）

为了让 opencode 的 cwd 回填，我执行了「**删掉 opencode 的派生事件 + 游标，再重扫**」。
但 `Store.insertEvents` 用的是 `INSERT OR IGNORE`，而这期间 **opencode 已经自己裁剪了历史**：

| | 修复前 | 重扫后 |
| --- | --- | --- |
| opencode 事件 | 2,443 | 979 |
| opencode token | 527.69M | 197.48M |
| 全库事件 | 92,852 | 91,572 |
| 全库 token | 14.43B | 14.135B |

源库里现在只剩 983 条 `session_message`（`event` 表 0 行），**约 1,464 条事件 / 330M token
无法找回**。这是「为了回填一个字段而删除行」造成的，正确做法是
**就地 `UPDATE` 已有的 cwd**，而不是删了重扫。

教训：本项目的 `INSERT OR IGNORE` 意味着本地库是**只增的历史归档**，
一旦删除就可能永久丢失（带 `cwd` 的旧行反而不会丢）。

### 7. 卡片布局修正

4 张卡变 3 列后，1×4 的指标网格把 `543m16s` 和 `641 tok` 挤到重叠。
改成 **2×2**，并把累计时长换成紧凑格式（`543m16s` → `9.1h`，新增 `fmtSpan`）。

## 第五轮：写入语义改为「补空不覆盖」

用户同意把 `insertEvents` 从 `INSERT OR IGNORE` 改成冲突时 `DO UPDATE`。

### 改法

- 冲突时**只补空、不覆盖**，与 `upsertSession` 同一套规则：
  **新值非空则以新值为准，新值为空则保留旧值**。
  - 补空字段：`cwd` / `session_id` / `model`（`'unknown'` 视为空）/ `provider` /
    `protocol` / `surface` / `originator` / `status` / `cost_usd` / `cost_source`
  - 耗时用 `MAX()`：`latency_ms` / `ttft_ms` 拿 `0` 当「当时还没采到」的哨兵，
    取较大值意味着以后补上 Codex TTFT 采集时，重扫就能就地填进来。
  - **刻意不动**：`ts` / `day` / `hour` / `tool` / 各类 token 计数 / `success`。
    这些是账本上的既成数字，重扫不该悄悄改写总量；真要重算走「清库重扫」。
- 「新增条数」不能再靠 `changes()`（upsert 对插入和更新都返回 1），
  改为先按 400 个一批查哪些 `event_id` 已存在，再算差集。

### 验证

- 新增 3 个回归测试（`store.test.js`）：就地回填 cwd 但 token 计数不变、
  空值不抹掉已知字段且 model 不退回 `unknown`、批量重复 id 只算一次新增。
  共 **173/173** 通过。
- 真库重扫：**新增 54 条（全部是真实新数据）**，总量 91,572 → 91,626，
  cwd 覆盖没有回退，opencode 保持 1014/1014。扫描后 `rebuildRollups()` 照常执行，
  所以 model 补空带来的分组变化会同步到日聚合。

### 效果

从现在起，修好某个采集器之后**直接重扫就能回填**，不必再删数据——
第四轮那种「删了才发现源库已裁剪」的路径被彻底堵住。

## 第六轮：购买力页重做（图标 + 趣味性）

用户要求：图标要「更精致、更接近实物」，功能设计要「更有趣味性，满足好奇心和情绪价值」。

### 1. 图标：emoji → 手绘 SVG 线稿

16 件商品各画一张矢量线稿（`web/src/mall-icons.ts`，纯数据），
统一 32×32 网格 / 描边 1.4 / 圆头圆角 / 图案收在 3..29 / 一律 `currentColor`。

放弃 emoji 的理由：emoji 是字体，形状由系统决定，颜色固定跟不上主题，
小尺寸糊成一团。第一版渲染出来后发现并修掉的 4 处：
钓鱼竿的绕线轮与浮标不成形、摩托车轮廓偏弱、手柄下沿多一根杂线、
显卡供电口悬空 + 金手指像两只脚（改成一条 PCIe 条）。

分享卡片走 `iconDataUrl()` 把**同一份**线稿序列化成 data URL 再 `drawImage`——
canvas 不认 JSX，而 data URL 不产生网络请求。

### 2. 趣味性：三个新增

| 新增 | 满足什么 | 实现 |
| --- | --- | --- |
| **每个编码小时 ¥54** + 每件商品「≈ N 小时」 | 好奇心：把总额折成自己的时间 | `perHour = 预算 / 活跃小时` |
| **「再写 N 天」** | 情绪价值：差额变成有重量的天数 | `daysTo = 差额 / 日均成本` |
| **「乱花一通」** | 趣味 + 分享：一次性随机小票 | `randomCart()`，按**单价加权**，可注随机源做确定性测试 |

「乱花一通」刻意不是均匀随机——均匀随机会退化成「一百多包咖啡豆」，
因为最便宜的商品永远买得起。

### 3. 商品卡改成图录条目

图标左上、目录编号（№05）右上、价格 + 折合小时、能买几件；
**买不起的不再只给一个差额，而是给一条进度条**——
看着条子已经走到 88%，比看到一个金额更想把它填满。

### 4. 一个真 bug

「每个编码小时」一开始算成 **¥848**。原因是我用了
`rate.overall.activeHours`，而它其实是「有请求**完成**的秒数 / 3600」
（85,114 秒 = 23.6 小时），根本不是编码时长。
正确的分母是**各天活跃分钟之和**（22,047 分钟 = 367 小时）→ **¥54.5/小时**。
